# SentinelGate v1.1 C2 Guard Design

## Goal

Add defensive detection of suspicious periodic outbound communication while preserving SentinelGate v1.0 firewall functionality.

## Architecture

Existing firewall monitoring continues to handle nftables firewall events and port-scan detection.

A new C2 Guard component analyses outbound network observations for repeated communication patterns such as periodic beaconing.

C2 Guard produces standard SentinelGate Event objects so alerts can use the existing SQLite event database, API, reporting, and dashboard architecture.

## Safety

C2 Guard does not directly modify nftables.

Any future automated blocking must go through FirewallService so existing IP validation, management-network protection, temporary bans, and audit logging remain enforced.

Initial development uses synthetic network observations rather than malware or real command-and-control infrastructure.

## Initial detection

The first detector will evaluate repeated connections to the same destination using:

- observation count
- time intervals
- average interval
- timing jitter
- configurable thresholds

Low timing jitter across repeated outbound connections may generate a suspected C2 beacon alert.

## Limitations

SentinelGate does not decrypt HTTPS and cannot determine application-layer content from encrypted traffic.

A beaconing detection represents suspicious behaviour, not proof of malware.
