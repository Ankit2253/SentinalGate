# SentinelGate v1.1 — C2 Guard and Analyst Response Design

## Goal

SentinelGate v1.1 extends the v1.0 Linux firewall foundation with defensive detection, investigation, and analyst-controlled response capabilities while preserving safe-by-default firewall behavior.

The v1.1 design intentionally separates **detection from enforcement**.

A suspicious C2 detection does not automatically change nftables policy. Blocking requires an explicit analyst-approved action through the existing SentinelGate response path.

## Architecture

SentinelGate v1.1 consists of the following major components:

- Stateful nftables firewall foundation
- Firewall event monitoring
- Port-scan detection
- C2 Guard behavioral detection
- Threat-intelligence enrichment
- Trusted-destination allowlists
- Detection confidence controls
- SQLite event persistence
- FastAPI control plane
- Local SOC dashboard
- Analyst-approved response
- Dynamic ban and unban controls
- Ruleset snapshots and rollback
- Response audit events
- systemd and Linux hardening controls
- Yocto/BitBake integration layer

The C2 Guard processing flow is:

```text
Network observations
        |
        v
C2 Guard
        |
        +--> Group by destination/protocol/port
        |
        +--> Calculate communication intervals
        |
        +--> Evaluate relative timing jitter
        |
        +--> Apply confidence threshold
        |
        +--> Check trusted destinations
        |
        +--> Enrich with local threat intelligence
        |
        v
suspected_c2_beacon Event
        |
        v
SQLite event database
        |
        +--> API
        |
        +--> Dashboard
        |
        +--> JSON evidence/reporting
        |
        v
Analyst review
        |
        v
Explicit analyst-approved response
        |
        v
FirewallService.ban()
```

## C2 Guard Detection

C2 Guard analyzes outbound network observations for repeated communication patterns that may represent beaconing behavior.

Detection considers:

- destination IP
- destination port
- protocol
- observation count
- communication intervals
- mean interval
- relative timing jitter
- detection confidence

Low relative jitter across repeated outbound observations can generate a `suspected_c2_beacon` event.

A detection represents suspicious behavior and is not treated as proof of malware or command-and-control activity.

## Threat Intelligence

SentinelGate v1.1 includes local threat-intelligence enrichment.

Configured IP indicators are loaded into `ThreatIntelligence` and matched against C2 Guard destinations.

Threat-intelligence matches can enrich detections with additional context and influence alert severity.

The initial implementation intentionally uses local configured indicators rather than automatically downloading or trusting external feeds.

## Trusted Destinations

Known-safe destinations can be configured through the C2 Guard trusted-destination list.

Observations directed to trusted destinations are suppressed from C2 Guard alert generation.

This provides an explicit false-positive reduction mechanism.

## Confidence Controls

C2 Guard supports a configurable minimum-confidence threshold.

Detections below the configured threshold are not emitted as C2 security events.

This allows detection sensitivity to be adjusted without modifying detector code.

## C2 Guard Enable/Disable Control

The configuration includes:

```toml
[c2_guard]
enabled = true
```

When C2 Guard is disabled:

- C2 observations are not analyzed
- C2 alerts are not generated or stored
- the service reports C2 Guard as disabled

This behavior is covered by regression tests.

## Detection and Enforcement Separation

The most important safety property of v1.1 is:

```text
C2 detection != firewall enforcement
```

`BeaconDetector` and `ThreatIntelligence` do not directly invoke nftables, subprocesses, firewall apply operations, or ban operations.

C2 analysis stores security events only.

A dedicated regression test verifies that generating a C2 detection does not automatically create an active firewall ban.

## Analyst-Controlled Response

An analyst can explicitly respond to a stored C2 alert.

The response path is:

```text
Stored suspected_c2_beacon event
        |
        v
Authenticated API request
        |
        v
FirewallService.respond_to_c2_alert()
        |
        +--> validate event exists
        +--> validate event is a C2 Guard alert
        +--> validate destination IP
        |
        v
FirewallService.ban()
```

The response reuses SentinelGate's existing ban implementation rather than creating a separate enforcement mechanism.

This preserves:

- IP validation
- management-network protection
- timed bans
- database persistence
- nftables backend controls
- existing audit behavior

## C2 Response Audit Trail

An analyst-approved C2 block creates a dedicated `c2_response` event.

The audit event records:

- original C2 event ID
- destination IP
- destination port
- protocol
- analyst-provided reason
- response type (`analyst-approved-block`)

This creates an explicit relationship between:

```text
Original C2 alert
      ->
Analyst decision
      ->
Firewall response
      ->
Reason/evidence
```

The normal `dynamic_ban` event is also retained.

## Unban and Reversibility

Analyst-created bans can be removed through the existing SentinelGate unban path.

Successful unban operations create a `dynamic_unban` security event.

Regression tests verify that a C2 response can be:

```text
Detected
   ->
Blocked by analyst
   ->
Unbanned
   ->
Audited
```

This ensures response actions remain reversible.

## Ruleset Rollback

SentinelGate preserves the v1.0 snapshot and rollback architecture.

Firewall deployments create ruleset snapshots.

A previous snapshot can be restored using the controlled rollback path.

Rollback operations create a `ruleset_rollback` event containing:

- source snapshot ID
- new snapshot ID representing the restored configuration

Real firewall rollback requires explicit confirmation when SentinelGate is operating in apply mode.

Regression tests verify rollback audit behavior.

## API Security

State-changing API operations use the authenticated `/api` router.

The analyst C2 response endpoint therefore inherits SentinelGate's bearer-token authentication controls.

Errors are safely translated into API responses rather than exposing raw backend exceptions.

The API continues to default to loopback binding unless appropriate authentication configuration is supplied.

## Dashboard

The SentinelGate dashboard provides C2 Guard visibility including:

- enabled/disabled status
- total C2 alerts
- high-severity C2 alert count
- recent C2 detections
- destination information
- confidence information

Dashboard C2 data is retrieved using the existing centralized API helper.

## Event Persistence and Reporting

C2 detections and response events use SentinelGate's existing generic `Event` model and SQLite event database.

This allows C2 activity to participate in:

- event history
- dashboard investigation
- API retrieval
- statistics
- evidence export
- incident reporting

JSON reports can include recent events, active bans, firewall rules, statistics, and snapshot history.

## Hardening

SentinelGate retains service-level hardening including:

- dedicated `sentinelgate` user/group
- `NoNewPrivileges`
- restricted capability set
- `CAP_NET_ADMIN`
- `CAP_NET_RAW`
- `ProtectSystem=strict`
- `ProtectHome=true`
- kernel/module/control-group protections
- restricted address families
- controlled writable state directory
- restrictive process umask

Only capabilities required for firewall/network operation are retained.

## Yocto Integration

SentinelGate v1.1 includes a custom Yocto layer:

```text
yocto/meta-sentinelgate/
```

The layer contains:

- SentinelGate v1.1 application recipe
- SentinelGate systemd service
- safe dry-run configuration
- Python application source
- dashboard static assets
- SentinelGate hardening recipe
- sysctl hardening configuration
- systemd hardening drop-in
- tmpfiles configuration
- minimal SentinelGate security image recipe

The v1.1 application recipe is:

```text
sentinelgate_1.1.0.bb
```

BitBake metadata parsing has been validated successfully and SentinelGate resolves as version `1.1.0`.

The complete BitBake package/image build is intentionally deferred to a later integration milestone and is not a blocker for the current v1.1 software release.

## Safety Principles

SentinelGate v1.1 follows these principles:

1. Detection does not automatically imply enforcement.
2. C2 Guard cannot directly modify nftables.
3. Analyst approval is required for C2 response.
4. Response uses the existing validated firewall service path.
5. Protected management addresses cannot be banned.
6. Response actions are auditable.
7. Bans can be reversed.
8. Rulesets can be rolled back.
9. Dry-run remains the default firewall mode.
10. Synthetic observations are used for safe C2 testing.

## Limitations

SentinelGate does not decrypt HTTPS or inspect encrypted application-layer content.

Beacon detection is behavioral and can produce false positives or false negatives.

Local threat intelligence requires manual indicator management.

C2 Guard currently analyzes supplied network observations rather than performing full packet capture or deep-packet inspection.

SentinelGate is an educational and portfolio defensive-security platform and is not an independently audited production firewall appliance.

The complete Yocto BitBake build and image validation are deferred to a later integration milestone.
